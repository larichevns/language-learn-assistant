# Записи адаптивного цикла обходят propose/Apply — это derived-state, а не предложения модели

**Решение.** Записи Phase-5 цикла — строка `Attempt`, пересчёт `masteryScore` (BKT), расписание FSRS (`SrsCard`/`GrammarCard`), `TimelineEvent`, `weakAreasJson` из ночного rollup — пишутся **напрямую**, не через [[Записи-это-proposals-единственный-путь-записи-Apply]].

**Почему это не нарушает гейт.** propose→Apply существует, чтобы **модель** никогда не писала авторский контент ученика. Но эти записи — **детерминированное серверное производное от собственного оценочного действия ученика** (он отправил ответ; он сам поставил грейд карточке). Модель тут вообще не участвует. Это ровно тот же класс, что и существующий путь SRS-ревью, который уже пишет `SrsCard` + `Review` напрямую (`app/api/vocabulary/review/route.ts`) без предложения.

**Источник истины — append-only логи** (`Review`, `Attempt`). Снапшот-поля (`masteryScore`, `weakAreasJson`, `errorSummaryJson`) — это **кэши, пересчитываемые из логов**; их перезаписывает ночной rollup ([[PWA-офлайн-SW-кэширует-чтения-IndexedDB-outbox-копит-записи]] — аналогичный принцип «лог это правда, снапшот это кэш»). Поэтому конкуренция за один топик не страшна: лог не конфликтует (только добавление), а BKT-снапшот — read-modify-write внутри транзакции грейда, где last-writer-wins на *кэше*, а rollup сверяет.

**Что это значит на практике.** Модель остаётся non-writer'ом; действия ученика детерминированно двигают derived-state. `weakAreasJson` теперь rollup-derived — ручная правка через LEARNER_PROFILE proposal переживётся до следующей ночи (это сознательно). См. [[phase-5-implementation-plan]] §0.
