# PWA-офлайн: SW кэширует чтения, IndexedDB-outbox копит записи

Полный офлайн для PWA разнесён на два механизма — **чтения через service worker, записи через клиентский outbox**. Без новых зависимостей (без Workbox/Serwist/idb).

## Чтения — service worker (`public/sw.js`)
- **Статика** (`/_next/static/*`, иконка, манифест) → **cache-first** (иммутабельно).
- **Страницы + RSC-пейлоады** → **network-first**, при офлайне отдаём из кэша, иначе синтезируем офлайн-HTML прямо в SW (не отдельный route — иначе middleware редиректит на `/login`).
- **Очереди повторений** `GET /api/vocabulary/review` и `/api/grammar/review` → **network-first с фолбэком в кэш** → ревью работает офлайн (страница + очередь берутся из кэша после первого онлайн-захода).
- Остальные `GET /api/*` → только сеть (не кэшируем изменяемые данные). Любой не-GET → мимо (записи идёт outbox).
- SW регистрируется **только в production** (`components/sw-register.tsx`) — в `next dev` его нет; проверять офлайн нужно на `next build && next start`.

## Записи — IndexedDB-outbox (`lib/offline/outbox.ts`)
- `postOrQueue(url, body)`: пробует POST; если **сеть недоступна** (`fetch` кидает `TypeError`, либо `navigator.onLine===false`) — кладёт запись в IndexedDB и резолвит `{queued:true}`, чтобы UI шёл дальше. **Ответ сервера (4xx/5xx) — это НЕ офлайн**, такую ошибку пробрасываем (`isNetworkError` отличает по `ApiClientError`).
- `flushOutbox()`: проигрывает очередь старейшими вперёд; останавливается на первой сетевой ошибке (повторит позже); дропает запись на 4xx (протухла/дубль — иначе очередь застрянет навсегда), держит на 5xx.
- `OfflineSync` (в `app/(app)/layout.tsx`) флашит **при `online`, при возврате фокуса вкладки, на маунте и по таймеру 20с** — таймер закрывает кейс «сервер вернулся, но интерфейс сети не падал» (на нём `online`-событие не стреляет).

## Почему outbox, а не Background Sync API
iOS Safari **не поддерживает** Background Sync. Клиентский outbox + флаш по нескольким триггерам работает везде, включая установленную PWA на iOS. Это сознательная замена [[Записи-это-proposals-единственный-путь-записи-Apply]]-агностичная: грейды — это детерминированное состояние из действий ученика (как и весь Phase 5 loop), не предложения модели.

## Проверено вживую (kill-server = офлайн)
`next build && start` → зашли онлайн (SW закэшировал страницу+очередь) → **убили сервер** → перезагрузка `/vocabulary/review` отрисовала карточки из кэша → грейд офлайн ушёл в outbox (`{grade:4, RU_TO_DE}`), индикатор «1 к синхронизации» → подняли сервер → на перезагрузке flush проиграл POST → в БД `Review +1`, `Attempt(SRS_REVIEW) +1` ровно с тем же грейдом, outbox пуст.

## Известные ограничения (в [[post-mvp-backlog]])
- Клиентская навигация (через `Link`) офлайн требует, чтобы страницу хоть раз открыли онлайн (RSC-пейлоад кэшируется network-first); первый офлайн-визит несохранённой страницы → офлайн-HTML.
- Кэш очереди привязан к юзеру; на общем устройстве это допущение single-owner.
- `navigator.onLine===true` при живом Wi-Fi, но мёртвом сервере — «Офлайн»-бейдж не покажется, но запись всё равно уходит в outbox (детект по `TypeError` от fetch).
