# Клиентский поиск по вкладке: переиспользуемый `SearchInput` + фильтр ДО группировки

Единый по-вкладочный поиск на всех 5 списочных страницах (`vocabulary`, `grammar`, `notes`,
`homework`, `exercises`) - **чисто клиентский**, без правок API/БД.

## Переиспользуемый компонент
`components/ui/search-input.tsx` (`SearchInput`) - контролируемое поле: ведущая лупа, хвостовая
кнопка-очистка (видна при непустом значении), `type="search"` + `role="searchbox"`,
`text-base` (16px, против iOS-zoom), **i18n-агностичный** проп `placeholder` (переводы
снаружи). Нативную вебкитовую крестик-кнопку глушим
(`[&::-webkit-search-cancel-button]:appearance-none`) в пользу своей. Родственный `SortToggle`
([[entryDate-это-пользовательская-дата-записи-отдельная-от-createdAt-сортировка-на-клиенте]])
повторяет тот же приём «лейблы приходят пропами».

## Паттерн: фильтр стоит ПЕРЕД группировкой
На каждой странице - `const [search, setSearch] = useState('')` + цепочка мемо в строгом
порядке:

```
items → filter(search) → sort(sortMode) → group/bucket → render
```

Фильтр-мемо (`filteredNotes` и т.п.) прогоняется **до** мемо группировки/бакетизации.
Поэтому заголовки групп и счётчики **пересчитываются над отфильтрованным набором** - группы,
опустевшие после фильтра, схлопываются, числа сходятся. Если бы фильтр стоял после
группировки, счётчики врали бы. Сорт по `entryDate` (feature C) встаёт **между** фильтром и
группировкой - пример в `app/(app)/notes/page.tsx`:
`filteredNotes → sortedNotes → notesByGroup/ungrouped`.

## Известное ограничение (сознательное)
Фильтр работает **только по загруженной странице** (≤100 элементов, React Query держит их
in-memory) - это не серверный поиск. На vocabulary/grammar серверный `?q=` в GET
**существует, но намеренно не задействован** - ради единообразия все 5 вкладок ведут себя
одинаково (in-memory фильтр). Настоящий серверный поиск включим, когда какой-нибудь список
перерастёт 100-элементный кэш - отложено в [[post-mvp-backlog]].
